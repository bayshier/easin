Uber 每月 100 万次 Agent Skill 调用，是怎么评估的

一个技能一年长到 5000 多个之后，问题就从「怎么写」变成了「怎么知道它好不好」。Uber 工程团队公开了他们的做法。这是我的解读，不是全文翻译。

原文 How Uber Evals 1 Million Agent Skill Invocations a Month（Uber Engineering，2026 年 11 月 23 日）· X 上的发布贴 ↗

先看数字

原文开篇给了三个数，是整篇文章的出发点：

1 → 5,000+共享技能市场里的技能数，2025 年 10 月到一年后
100 万+单月 agent 调用技能的次数
12 项为每个技能计算的指标，含用户数、留存、成本、延迟、错误

我更在意的是作者在文末说的那句话的重心变化：用量上来、模型变强之后，他们的焦点已经从「写技能」转到了「技能的质量与评估」。下面挑我觉得最有信息量的四块来讲。

一、评估集的配比：5 / 80 / 15

Uber 给技能做评估，不靠用户人工反馈。他们的评估集有明确的构成：

  • 约 5% 黄金用例：输入固定、输出可预期、工具用 mock。
  • 80% 真实 prompt，按轨迹打分。轨迹看的是 agent 有没有按正确顺序用了正确的技能和工具，不看最终结果。
  • 15% 由作者判断。

有两个说法和常见直觉相反，值得记下来。一是通过率 70% 到 90% 的评估，可能比 100% 通过的更有用：答案会变，裁判也会变；满分往往意味着这个评估没捕捉到答案里有意义的变化。二是评估必须在干净环境里跑（他们用了后台 agent 平台、托管沙箱和远程开发机三种），因为干净环境能揪出那些「在我机器上是好的」的依赖——有的技能需要特定文件路径、缓存过的文档或特定系统的工具才能工作。

二、消融实验：把技能拿掉，看答案会不会变差

这是我认为最可直接借鉴的方法。对同一个技能，把真实 prompt 回放两次，一次带技能、一次不带，让一个不知情的裁判选更好的答案。

原文给的例子是数据仓库查询技能：不带技能的会话多发了 13% 的工具调用，工具错误多出六倍，耗时多出 31%；带技能的答案在 87% 的对比中胜出。

结论是少有时反而是多。模型越强，技能里多出来的文字越可能拖累表现，所以他们也会测试从技能里删词。作者同时说得很清楚：收益最大的是那些给了 agent 它原本找不到的东西的技能，比如访问内部文档的途径。

三、Code Mode：超过 100 个工具时，光定义就吃掉五到七万 token

LLM 客户端默认的 MCP 安装方式，会把每个工具的完整描述塞进每一次调用。原文说工具超过 100 个时，用户还没打字，这些定义就占了 50,000 到 70,000 个 token。

Uber 受 Cloudflare 的 Code Mode 启发，把这些流程移进工具脚本，由脚本通过网关调工具，agent 只读结果里它需要的部分。他们还禁止在技能和插件里使用 .mcp.json。另外几条降本手段也都有前后数据：技能放到更便宜的模型上跑，单次调用成本降了 46%；技能加载时就跑脚本省掉一轮，降了 32%；花费最高的 20 个会话里，通知轮次约占三分之一的花费，于是把轮询挪到了后台。

四、Agent 自己报 bug

agent 遇到坏掉的参数、错误的文档、静默失败的命令时，往往能找到变通办法，但会白白烧掉大量 token。Uber 加了一个常开技能 log-papercut，让 agent 把遇到的阻力提交成结构化报告，他们把每份报告叫一个 papercut。报告要写明尝试了什么、预期什么、实际发生了什么、怎样才算修好。

三个月里 agent 提交了数千份，已修复数百个。原文列的几个例子很具体：某个 pull request 技能把提交信息写进共享临时文件，两个并发会话会改到彼此的 PR；部署技能让 agent 传 epoch 秒数，而 API 要的是毫秒。

和我自己做的两个仓库对照

我之前做过两个相关的小项目，量级和 Uber 没法比，但对照着看，能看清哪些地方想对了、哪些地方差得远。

主题Uber 的做法我的仓库差距
技能演进 先写 spec，工具从 spec 编译出 SKILL.md 和测试 prompt；模型变了就重新编译 harness-engineering：观察 → 本能 → eval 门控 → 真实 git 提交 → 可回滚 Uber 的单元是「spec」，我的单元是「技能」本身；他们多了一层与模型无关的意图
评估 5/80/15 配比、三种干净环境、消融实验、盲评 单测 9 项，覆盖门控和回滚的逻辑是否正确 最大的一块。我验证的是「机制能跑」，没有验证「技能有用」
质量检查 Linter：步骤编号、每步一条具体命令并检查结果、必须有错误恢复表 android-agent-skills：5 个从真实 Android 项目里蒸馏出的技能 方向一致，但我没有把标准固化成 linter，只是写的时候照着做

诚实地说，我的 harness-engineering 里的自进化循环，验证的是「弱技能会被门控拒绝、好技能会提交」这套机制本身，用的是确定性脚本 agent 和 9 个单测。它证明不了某个技能在真实任务上有没有用。Uber 用消融实验和盲评回答的正是这个问题。

如果只带走三条

  • 用「拿掉它会不会变差」来检验一个技能。不需要复杂的基础设施，回放几次真实 prompt、找人盲评，就能得到答案。
  • 工具一多，定义本身就是成本。原文的数字是 100 多个工具、五到七万 token。能写进脚本的流程就别让模型每轮重读一遍定义。
  • 满分不是好评估。70% 到 90% 通过率可能更真实。

说明

这是我的解读，不是译文；文中数字均出自原文，建议读原文全文。原文还有几块我没展开：三层技能市场、aifx 如何让一份配置对多种 agent 生效、技能发现、以及成本的具体度量方法。原文同时提到未解决的开放问题是「如何评估很少运行、但很重要、又很难判断的工作流」，并说下一步要做技能的 A/B 测试和按模型编译。
